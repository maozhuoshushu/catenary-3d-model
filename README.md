# 接触网三维模型 · 零件算子库

> 铁路接触网（OCS, Overhead Catenary System）的**参数化三维建模**：
> 一套零依赖的零件算子库，以及由它生成的四个**单文件、离线可用**的成品模型。
>
> **English**: Parametric 3D modelling of railway overhead catenary systems.
> A dependency-free part-operator library plus four self-contained, offline,
> single-file WebGL models. No build step, no CDN, no network access.

---

## 1. 这是什么

铁路接触网的零部件种类多、装配关系强、尺寸受多本标准与图纸交叉约束。
本项目把「**零件 → 装配 → 布局**」这条链拆成可复用的算子，再用它拼出成品模型。

| 目录 | 内容 |
|---|---|
| `算子/零件算子/` | **零件算子库** `parts.js` ＋ 自校验脚本 `verify_parts_lib.py` |
| `算子/算子核心/` | **几何核心** `geom.js` ＋ 单元测试 ＋ 迁移/嵌套审计工具 |
| `算子/接口规范_零件资产.md` | 零件资产**接口规范**（三条硬契约，见 §4） |
| `算子/样板/空白中间柱.html` | **空白样板**：不含任何算子源码，入库即用 |
| `模型/` | 四个成品模型（见 §2） |

## 3. 技术要点

**自研微型 WebGL 引擎**（无 three.js 等任何依赖）：

- `BUF` 顶点缓冲 → `part()` 分组 → `withM()` **真矩阵栈** → `upload()` 交错打包
  （**14 个 float / 顶点**）→ 单次 `drawArrays` 提交；
- 自带**阴影通道**（`SHADOW_SIZE = 2048` 深度贴图）、拾取（`pick`）、剖面、标注层；
- **设备像素比（DPR）自适应**，随窗口尺寸重建画布。

**受电弓是真 3D，不是贴图或叠加层**：

- 与模型**共用同一个 WebGL context 与深度缓冲**，在模型本帧画完后用**同一套
  proj/view 矩阵** `drawArrays` → 因此导线、腕臂、支柱与受电弓之间
  **遮挡关系真实正确**（受电弓该被导线挡住的部分就会被挡住）；
- 与模型同批 `requestAnimationFrame`，模型先跑；
- ⚠ 实现细节：绘制后必须还原 `BLEND` 状态，否则若阴影通道关闭会污染后续帧。

## 4. 三条硬契约（摘自 `接口规范_零件资产.md`）

> 「可拼接」的前提不是零件画得多细，而是**每个零件都遵守同一份契约**。

1. **单一事实来源** —— 一个几何量只在一处算出，其它地方引用；禁止同一量在多处各写一遍字面量。
2. **不得依赖隐式前提** —— 语义必须写进代码，不能靠"当前数据恰好满足"。
3. **无模块级可变状态** —— 零件函数必须是"参数进 → 几何出"的纯函数。

这三条不是纸上设计，**每一条都是从一个真实事故里长出来的**（规范文档内附四例反面实证）。

## 5. 审计接口

模型暴露 `window.__CAT`，供自动化核验几何，避免"目测验收"：

```js
__CAT.PT              // 零件类型表（84 个 id）
__CAT.PARTNAME        // id → 零件名
__CAT.partGeom(id)    // → { id, name, verts, tris, points[] }
__CAT.dumpScene()     // 全场景快照
__CAT.pick(x, y)      // 屏幕坐标拾取
__CAT.look(...)       // 机位
```

骑乘视角版另有 `window.__RIDE`：

```js
__RIDE.enter() / exit()
__RIDE.state          // { on, x, v, mult, off, panto, ... }
__RIDE.project(p)     // 世界坐标 → 屏幕 { x, y, w }
__RIDE.glInfo()       // → { ok, tris, ctx, size }
```

**验收口径**：几何结论一律以**工具回读**为准，不以截图目测为准。
本仓库的算子库附带 `verify_parts_lib.py`，用 Möller–Trumbore 三角级求交、
逐件顶点哈希、帧内 `gl.readPixels` 回读来比对，并内置**负控**（故意注入偏差，
必须报错才算校验器本身有效）。

## 6. 低配档（无显卡机器）

面向 **Windows 7 + 老 CPU + 小内存 + 无独立显卡**（浏览器会退回 SwiftShader 纯 CPU 光栅）
的场景，`..._低配.html` 做了三组降载：

| 组 | 改动 |
|---|---|
| **像素** | DPR 上限 2 → 1；加**像素预算** 1280×720，超出则等比缩画布（CSS 仍铺满窗口） |
| **三角** | 顶点按 **10 m 线路分块**重排，每帧**只提交相机 ±60 m 范围内的块**；阴影通道默认关闭 |
| **面数** | 圆柱／球／多段管**段数折半** |

**关键约束**：分块重排**只重排送往 GPU 的那份数组，原始顶点缓冲一字不动**
⇒ `partGeom` / 审计 / 拾取的语义完全不变。

实测（开发机 RTX 4060，**非目标机**；每帧量由 `drawArrays` 插桩、3 帧采样）：

| 量 | 标准版 | 低配档 | 变化 |
|---|---|---|---|
| 全场景三角（逐件合计） | 516,746 | 289,234 | **−44%** |
| 全场景顶点 | 1,550,238 | 867,702 | −44% |
| 画布像素 | 2400×1401 = 3.36 Mpx | 1256×733 = 0.92 Mpx | **−73%** |
| **每帧提交三角** | 1,060,725 | 169,139 | **−84%** |
| **每帧光栅像素**（含阴影通道） | 3.36 ＋ 4.19 = 7.55 Mpx | 0.92 Mpx | **−88%** |
| 每帧 draw call | 3 | 15 | ＋12 |
| 阴影通道 | 开（2048²） | 关 | — |

> draw call 从 3 涨到 15，是分块剔除把一次全场景提交拆成了多个小批次——
> **换来了 84% 的三角削减**，这个交换是划算的。

> **内存才是低配机器的真正瓶颈**：顶点 JS 数组约 150–200 MB，加上交错
> `Float32Array` 约 89 MB 与 GPU 副本约 89 MB。因此**降低面数是必需项，不是可选项**。

**兼容性**：全部代码为 **ES5**（无箭头函数／模板字符串／`let`/`const`），
Windows 7 上封顶的 Chrome 109 可直接运行。
若无显卡机器上用的是较新版 Chrome，可能需加启动参数
`--enable-unsafe-swiftshader`（或 `--use-angle=swiftshader`）才允许建立 WebGL 上下文。

## 7. 运行

```bash
# 直接打开（推荐）
双击「模型/」下任一 .html

# 或起个本地静态服务器
python -m http.server 8000
# → http://localhost:8000/模型/
```

算子库自校验（需要一个模型文件在同级 `模型/` 目录）：

```bash
python 算子/零件算子/verify_parts_lib.py            # 正控：应 EXIT 0
python 算子/零件算子/verify_parts_lib.py --negctl   # 负控：应 EXIT 1
```

若模型不在默认位置，用环境变量指定仓库根：

```bash
CATENARY_ROOT=/path/to/catenary-3d-model python 算子/零件算子/verify_parts_lib.py
```

## 8. 关于本仓库

**本仓库只包含算子与模型本体。**
项目的参考资料（内部图纸、技术标准扫描件、现场照片、装配数据台账等）**均未包含**，
也不在版本历史中。

发布副本已做**去内部出处处理**，具体为：

- 移除模型内嵌图纸索引中的**内部文件路径与文件哈希**；
- 内部图号统一替换为中性代号（如 `1002-03` → `R-M1`、`1003-04` → `R-J2`）；
- 移除内部线路名、内部图册名与内部文档目录引用；
- 移除开发机绝对路径。

**经过验证**：替换前／替换后的逐件几何签名**完全一致**
（84 件、1,550,238 顶点、516,746 三角面，逐件顶点哈希逐位相同），
四个模型的渲染与交互行为一致。

**保留**：`TB/T` 等**国家/行业公开标准**的引用（正常工程实践，非内部资料）。
